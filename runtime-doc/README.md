# Independent DOC implementation — Issue #11

## Current independent execution profile — autonomous scaling candidate

The application source describes typed dependencies and runtime-sized finite families, not hardware thread counts. In the independent implementation, CPU worker admission uses process affinity, cgroup CPU quota and admitted ready work. The operator may bound the CPU pool with `DOC_WORKERS`, but no source or automatic benchmark requires it. Nested pools remain suppressed. Explicit `--backend=gpu` is strict; `--backend=auto` enables the existing automatic mixed placement policy, with eligibility checked before dispatch. CPU remains the default when no backend is requested.

The fixed 4,096-lane family ceiling of the frozen reference is superseded in this candidate. Ordinary independent application lists and families use the checked region byte budget, while compiler workspaces, source-stream, text, natural, causal and other independent bounds remain separately enforced. Per-region aggregate allocation and device-specific binding and buffer limits can reject an otherwise representable extent. No promise of unbounded host or device memory is made. Input parsing preserves exact signed-64-bit semantics and malformed-input rejection.

The DOC-authored GPU planner retains conservative legacy bounds and additionally proves supported signed-32-bit expressions, including positive-literal quotient and remainder. No general arithmetic wraparound, dynamic-divisor admission, arbitrary managed-value shader, or unrestricted GPU recurrence is claimed. A compact single family selector and grid-stride WGSL cover all admitted lanes. The portable local workgroup width is 64; the total group count is computed from the actual workload and negotiated device limit, not a per-workload tuning constant or a requested GPU thread count. Physical GPU scheduling is controlled by the provider. The existing automatic device threshold is a generic heuristic, not globally optimal profitability.

Production candidate and acceptance: [physical-only integrated workflow 46052437755](https://github.com/xad3play/DOC/actions/runs/46052437755); [CPU/compiler preflight 46052604155](https://github.com/xad3play/DOC/actions/runs/46052604155). Older measurements below document historical implementations, not current limits. The final campaign builds GPU binaries on GitHub without opening an adapter and runs them on actual Kaggle hardware. The standard staged sort/reduction benchmark uses host stage orchestration; it is not a general on-device whole-program implementation. No paper or release status is implied.

## First executable slice

`compiler/lexer.doc` is DOC-authored, not a new Rust frontend or host parser. Given a sequence of UTF-8 byte values, a private causal scan emits immutable (token kind, byte offset, byte length) triples. Identifiers, decimal runs, quoted UTF-8 text, line boundaries, comments and punctuation are handled; invalid UTF-8, unsupported lexical bytes and unterminated/unsupported strings fail before the requested token result is published. Signs and arrow components are separate tokens. The current lexical profile is ASCII identifiers, no escape syntax, and no hash or line break in strings, matching the reference's line/comment restrictions. Syntax, numeric range, authority, typing, graph validity and import path semantics are later stages, not established by lexing.

The bootstrap test in `tests/test_lexer.py` uses a separate regular-expression oracle solely for testing. It compares actual token spans and invalid-input rejection under 1 and 4 worker settings, including the compiler source and an authored graphics stage; the native test invokes the generated executable from an empty directory. Frozen reference and actual native lexer passed 16 positive and 9 negative cases on commit 396807872f7f5c60414001cc619cfc3e4a1673fe, [CI 45542282787](https://github.com/rtu0/doc2/actions/runs/45542282787). The immutable recurrence uses bounded reference collections and copies growing state: no large-input or throughput claim, and it needs a production storage design. No Stage-1 self-hosting claim.

## Second executable compiler slice (candidate)

### Independent POSIX buffer profile

### Bounded independent graph-reader admission (candidate)

The prelinked graph host reserves a distinct physical reader slot before materializing a private immutable snapshot. The default host profile allows eight simultaneously active callbacks (compile-time configurable from 1 to 64). Exhaustion rejects a read without blocking graph replacement or allocating another snapshot; the caller may retry when a slot becomes available. Each callback owns its copy, with the existing bounded region capacity. The slot bitset is not a reference count and does not govern the lifetime of the retired graph. The graph mutex protects slot admission/release; release follows destruction of the private copy, including failed materialization. Callbacks must return normally, not retain pointers, and the host caller must quiesce all operations before destruction. This bounds concurrent reader retention, not arbitrary external callback memory. Local native ASan/UBSan slot tests passed 1,000 fill/reject/release/reuse cycles at each capacity 1, 8 and 64. The expanded Stage-2 graph test requires eight stalled readers through graph replacement, ninth-reader rejection, allocation-failure recovery, 64 further replacements and no live bytes; full integration under ASan/UBSan and TSan remains unverified until the next consolidated run.

### Bounded direct epoch snapshots (candidate)

### WebGPU submission retirement and protected cancellation (candidate)

The successful staging map remains the normal completion proof for a compute dispatch. A submitted dispatch without a successful map now requires the WebGPU queue completion callback before resource retirement/reuse, or a terminal device-loss acknowledgement. A failed queue completion poisons the device, explicitly destroys it if necessary, and waits for loss acknowledgement; a provider that never acknowledges causes bounded fail-stop without a new epoch publication. Only driver-owned handles are released after that boundary; there is no DOC-managed shared ownership or reference counting. The narrow pinned WebGPU ABI is the external device/resource lifetime boundary.

The separately built `gpu_epoch_authority_host.c` test admits a real mixed dispatch then stalls host acknowledgement before mapping; cancellation must retain the previous typed snapshot, reject publication, reclaim CPU candidates and allow a later GPU pool reuse. A test-only early abandonment after real submission must acknowledge queue completion before retry. Actual device destruction at the same boundary must retain the prior epoch and reject all new publication. This is a new candidate; actual-device execution and full ABI integration remain pending. Holding host acknowledgement after submit is not proof that the physical GPU was still executing at the exact moment of cancellation.

### Logical GPU buffer-pool accounting (candidate)

The GPU pool records the logical byte sizes of admitted WebGPU buffer handles, released handles, currently retained handles and their peak overlap during growth. Input bytes are charged once per admitted input buffer; selection, result and staging bytes are charged together only after successful admission. During growth, new handles are charged before old handles are released. Reuse must not change these counters. Closure must report zero live bytes and equal admitted/released totals. These counters do not measure physical VRAM, driver-internal storage or actual driver deallocation time. An isolated ASan/UBSan test passed 4,096 growth/retirement transitions and overflow/underflow rejection. The generated mixed-graph authority harness requires one-lane initial allocation, growth to a full frontier, overlap, subsequent reuse, cancellation, retirement and closure. The physical return validator independently checks byte conservation, monotonic accounting, growth, reuse, closure, typed output parity and actual adapter classification. Six offline evidence tests pass, including missing or inconsistent records; they are not GPU execution evidence. Both actual-device gates remain pending.
