# Source-only release candidate validation

This directory prepares a **development candidate**, not a public release. The candidate is exported into a clean directory from an exact Git commit. It excludes Rust/Goose evaluators, old CI, comparative investigations, historical evidence, generated policy headers, publisher class files pending permission review and the optional game distribution. The game has already been validated on development source; omission from this initial core candidate does not remove its release acceptance prerequisite.

The internal build job constructs a native bootstrap using the frozen reference in the development checkout. The separate clean candidate job receives only the native compiler bootstrap plus its digest, not the reference evaluator. Policy headers are regenerated from DOC source into the temporary build workspace. The candidate itself remains text-source-only; generated headers, executable outputs, manifests and logs are CI artifacts. The final distributed bootstrap still requires signed/hash-pinned provenance, rights review and clean reproducibility checks.

The clean-source job verifies native compiler self-reproduction, an independently checked compiled sample and native policy/authority/rollback regressions where executed. It does not establish final install packaging, physical GPU execution on the curated tree, a complete dependency/caller audit, licensing clearance, or release approval. See the development readiness register for open gates.

The isolated installation smoke copies the native Stage-2 compiler, scanner, build adapter and headers into an installation prefix, compiles an independent scalar/list fixture in a user workspace, relocates and executes the native output in a minimal environment, checks ELF linkage and rejects invalid typing, cyclic dependency and undefined-reference inputs without replacing prior successful outputs. Its evidence is generated outside the tracked source tree. This is a bounded CPU installation regression, not a full package installer or GPU qualification.

## Candidate-only numerical GPU smoke

The native rebuild also runs `test_gpu_candidate.py` in CPU-only mode by default. An independently computed integer-list oracle checks five epochs of runtime-sized work, with 128, 0, 256, 3 and 128 members. No original evaluator or deprecated example directory is needed. For a physical-device validation host, pass `--physical-wgpu-root /path/to/verified/wgpu` to the same clean rebuild command. The native Stage-2 compiler and scanner build the DOC planner from the curated source, and the test builds the same fixture into CPU and WebGPU/WGSL native programs. The physical mode requires actual physical adapter traces, expected family dispatch sizes, strict GPU admission and numerical readback, zero-extent behavior and rejection of out-of-range work; it cannot silently substitute a CPU or software adapter. The WebGPU ABI installation is an explicit external dependency; verify the exact upstream archive/version/digest and its applicable notices before use. Preserve the generated evidence, including raw streams and native/code hashes. This is a bounded candidate GPU smoke, not the full existing physical device-loss, graph-generation, and scaling campaign, nor an automatic Kaggle dispatch.

## Core candidate file inventory

The development exporter uses an explicit inventory of 76 maintained source and documentation paths rather than admitting every file with a matching extension. The optional game/graphics footprint is not distributed in this core candidate: the mesh compiler/frame utilities, mesh packet/render host and window-system/scene adapters are excluded. These files remain in the canonical development repository; this is not a removal from development or a decision to ship a game. The ordinary managed/reactive compiler, GPU planner and native scalar/standalone compiler sources remain available; the latter still require complete supported-profile and caller review. External build prerequisites are Python 3, a Linux x86-64 C toolchain and binutils; the core uses libc/POSIX, pthread and math interfaces, with the external WebGPU ABI for GPU builds. The core does not require the optional X11, Wayland or XKB graphics integration. This is a dependency-scope statement, not a rights clearance or a complete installable release.

## Build provenance gate

The internal candidate stage signs the exact tar, manifest, transported verifier, native managed and module_scan executables, and bootstrap checksum manifest with GitHub's pinned build-provenance attestation action. The clean job verifies each subject against the signed bundle, exact source SHA, master ref, repository and originating workflow before it executes any downloaded code. It then checks the bootstrap checksums, including toolchain/dependency records and linkage reports. The signature identifies the CI build; it is not a license grant, a guarantee of compiler correctness, or a final publisher release signature. No GitHub Release is created. Preserve the attestation bundle and verification records with the corresponding artifacts; a later distribution requires an explicit release decision and verification against a separately trusted release policy. See the [GitHub CLI verification reference](https://cli.github.com/manual/gh_attestation_verify).
